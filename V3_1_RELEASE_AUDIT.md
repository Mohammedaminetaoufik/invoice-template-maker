# InvoiceTemplateMaker V3.1 release audit

Date: 2026-10-15. Production release status: **not deployed**. This report separates the pushed baseline from local audit changes that still require owner review.

## Brand mark follow-up (2026-10-15)

A new vector InvoiceTemplateMaker mark in `app/icon.svg` replaces the generic document glyph in the EN/FR header, footer and root fallback. Next.js also exports the same mark as the browser icon. It uses the existing deep teal, white and orange palette; the wordmark remains selectable text. The logo belongs to the website only: uploaded customer logos and exported invoice PDFs remain unaffected. The updated static verifier checks the icon file, browser icon metadata and shared brand-mark references. `npm run check` passed 186 tests and the static export; a final EN/FR responsive sweep at 320–1440px found no overflow, page errors, external requests or clipped header controls. Header and footer screenshots at 320px were visually reviewed. This follow-up is local and uncommitted.

## Frontend assessment

The existing experience meets the intended template-first flow: an EN/FR hero links directly to creation, eight designs are visible before data entry, document fields can be edited directly, and mobile Quick Edit offers a native field selector. The completed invoice stays visible with Edit, Download again and Change template, followed immediately by Ternyxa and then FAQ content. The gallery comparison dialog, draft persistence, advanced settings and PDF preview were retained rather than redesigned.

The five-second comprehension goal is a design target, **not** a measured usability result. The mobile document is necessarily smaller than a printed page; the accessible text editor and Quick Edit selector make its fields editable without relying on tiny touch regions. A physical keyboard/zoom review remains outstanding.

## Deployment and review boundary

The static export remains in `out/`; `next.config.ts` and `wrangler.jsonc` retain the Cloudflare Workers Static Assets configuration. [Cloudflare's version documentation](https://developers.cloudflare.com/workers/versions-and-deployments/) says a version includes code, assets and configuration, while a deployment determines traffic. [`wrangler versions upload`](https://developers.cloudflare.com/workers/versions-and-deployments/version-urls/) creates a version URL without promoting production traffic. [Workers Builds settings](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/) can customize build and deploy commands. The remote dashboard's current production branch, build command, deploy command, non-production branch behavior and Version URL setting were **not accessible for verification** here. The owner should inspect those settings before any push that could trigger a connected build. The intended build command is `npm run build` and production version-upload command is `npx wrangler versions upload --config wrangler.jsonc`; the default `wrangler deploy` would publish to live traffic.

The new GitHub Actions file has no deployment command or secrets. Its first hosted status, branch protection and required checks cannot be asserted until the owner permits a push and reviews repository settings. A prepared PR description is in [docs/V3_1_PR.md](docs/V3_1_PR.md); no PR was opened against stale pushed code. Rollback after an approved deployment is via Cloudflare Deployments and requires a separate owner decision because [rollback changes live traffic](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/).

Owner dashboard review: in GitHub repository Settings → Rules/Branches, require the new `TypeScript, PDF, static export, browser, Cloudflare dry-run` job before merging to `main`. In Cloudflare Workers & Pages → `invoice-template-maker` → Settings → Builds, confirm the production branch, `npm run build`, a version-upload command for production, and the non-production branch behavior; save and re-open the settings to confirm. In Settings → Domains & Routes, check whether Version URLs are enabled and whether access protection is appropriate. These settings were not changed or verified remotely in this audit.
